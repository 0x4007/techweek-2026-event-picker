## 1. ICP focus for this conference

### Best buyers to prioritize
1. **CTO / VP Engineering**
   - Pain: AI code volume, review overload, shallow productivity metrics.
   - Ask: “Would you react to a 5-minute manager packet demo next week?”

2. **DevEx / Platform / EngOps**
   - Pain: invisible work, reporting, manager calibration, GitHub workflow evidence.
   - Ask: “Who owns contribution evidence or engineering operating metrics?”

3. **Open-source maintainers / DevRel / OSPO**
   - Pain: reward allocation, maintainer labor, triage/review/spec work not credited.
   - Ask: “Would a source-linked contribution ledger help with grants, bounties, or contributor programs?”

4. **AI-native founders / engineering managers**
   - Pain: agents blur authorship; humans still shape specs, reviews, prompts, and decisions.
   - Ask: “Which repo has enough issue/PR discussion for a one-repo pilot?”

### Disqualify fast
Avoid spending much time on:
- Pure investor conversations unless they can introduce CTOs.
- Generic AI founders without GitHub-heavy teams.
- Non-engineering GTM/marketing attendees.
- People who only want “developer productivity rankings.”

## 2. Core conference offer

### Main offer
**One-repo pilot**

> “Connect one GitHub repo, score recent closed issues and merged PRs, and export a manager packet showing who contributed, what counted, why it counted, which policy applied, and where the source evidence lives.”

### Pilot constraints
Keep it safe:
- GitHub-first.
- Read-only where possible.
- Non-compensatory at first.
- No Slack/HRIS/finance needed for first pilot.
- Human-reviewed output.
- Not a performance review replacement.

### Success criteria
A buyer should say:

> “This shows useful engineering work I do not get from commits or normal dashboards.”

## 3. Messaging to use all week

### 10-second version
> “Accolades turns GitHub work artifacts into source-linked contribution credit — specs, reviews, comments, and coordination, not just commits.”

### Safer version for skeptical rooms
> “It is not employee scoring. It is source-linked contribution evidence for work that already happened in GitHub.”

### 30-second version
> “Engineering teams increasingly rely on AI, but commits are becoming a worse proxy for contribution. Accolades creates a reviewable ledger from GitHub artifacts — issue specs, PR reviews, comments, and coordination — where every point has a contributor, reason, policy, and source link. The goal is a manager packet, not a leaderboard.”

### Best discovery opener
> “I’m working on an evidence-backed contribution ledger for engineering teams. It recognizes specs, reviews, comments, and coordination, not just commits. I’m trying to understand where this is useful versus dangerous.”

### Avoid saying
- “We measure developer productivity.”
- “We rank engineers.”
- “The AI decides who is valuable.”
- “We track Slack activity.”
- “This replaces performance reviews.”

## Sunday, May 24 — Objection handling

Prepare short answers.

### Surveillance concern
> “That concern is exactly why I avoid positioning this as productivity tracking. Accolades uses existing GitHub artifacts and source links. It is meant as reviewable evidence, not monitoring, ranking, or automatic performance management.”

### Gaming concern
> “Any incentive system can be gamed if it rewards raw activity. Accolades is designed around source-linked artifacts, relevance, policy controls, and human review.”

### Fairness concern
> “It is not a universal fairness engine. The goal is to make evidence inspectable and policy-governed so humans can interpret it with context.”

### AI distrust
> “No one should trust an unexplained AI score. Every record should show what counted, why, which policy applied, and where the source lives.”

### Slack concern
> “The direction is Slack-linked decisions tied to issues, PRs, or incidents — not raw Slack message scoring or DM analysis.”
